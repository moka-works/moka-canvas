# Moka Canvas

A React + LeaferJS visual consistency lab delivered through the same Rust localhost server in browsers and a Tauri desktop WebView.

## Prerequisites

- Node.js 22+ and npm
- Rust stable and Cargo
- Tauri platform requirements for the native target you build
  - macOS: Xcode command-line tools
  - Windows: Microsoft C++ Build Tools, WebView2, and WiX/NSIS as required by Tauri
- ffmpeg 5.0 or newer, with libass, for video export (optional: without it the cutting room works as it is and only the export says it is unavailable)

## Run locally

```sh
make install
make web-serve
```

Open `http://127.0.0.1:8080`. The server provides the built React application, SPA fallback, `/api/health`, and `/api/runtime` from one origin.

For the desktop container:

```sh
make tauri-dev
```

Tauri bundles the built `dist/` directory as a resource, starts the same Axum server on an ephemeral loopback port, and points its WebView to that URL.

## Configuration and data

Application-level state — model configurations, encrypted API keys, defaults and preferences, the recent-project list, and the prompt library — lives in one directory under the platform application-data location, never inside the program tree. Startup rejects a directory that resolves next to the executable, inside the served assets, or inside the working directory.

What a server listens on, how long it waits for a provider, and what it refuses to carry is deployment configuration instead, and the server needs none of it to start: with no file it runs on built-in defaults. `config/moka.yaml` is read when it is there and is never committed; `config/moka.example.yaml` is the tracked one, documenting every key and agreeing with those defaults line for line. See [docs/deployment.md](docs/deployment.md).

Three environment variables override the resolved values: `MOKA_METADATA_DIR` (location), `MOKA_METADATA_STORE` (only `file` is accepted), and `MOKA_METADATA_KEY` (the server-mode master key, base64 of 32 bytes). The directory must be on a local disk and must be used by one process at a time; a second process pointing at it fails to start and names the pid holding the lock.

A master key does not have to exist before the first API key is stored: one is generated into the OS keychain on a desktop, or into `<metadata.dir>/master.key` on a server started without `MOKA_METADATA_KEY`. The file tier is the weaker one — the key sits beside the ciphertext it protects — so export a key (`moka-server --generate-key` prints one) for any deployment that is not local and single-user. `/api/health` and the settings page report which tier is in use.

Each project document carries its own canvas schema stamp. Only the current schema is read: a document stamped otherwise is refused as an unsupported version rather than partially read or rewritten, and every node's ports are reconciled against the current port table as it loads. Read [docs/release-checklist.md](docs/release-checklist.md) before installing an older build over a newer one.

`GET /api/health` reports the store kind, the redacted root, the schema version, the secret-storage tier, and per-document state. `GET /api/ready` answers 503 until the assets are present, a write probe against the metadata directory succeeds, and any open project directory still exists.

Models and generation preferences are edited in the settings dialog, opened from the **Settings** button on both the launcher and the editor. There is no provider grouping: every model is a configuration of its own, listed under a tab per category — **Text**, **Image**, **Speech**, **Music**, **Video**, **Speech recognition** — and each carries its category, the protocol it speaks (chosen from the list that category offers — a list built from the converter scripts on disk, so a protocol is added by dropping a directory into the models tree rather than by writing code), the complete endpoint URL it is asked at, the model name the provider knows, a display name, and an API key of its own. A configuration can be duplicated in one action, key included, which is the quick way to add a second model at the same address. Each category's default model is the radio on its cards, chosen where the models are listed rather than on a page of its own. Model configuration lives under `/api/v1/models`. API keys are written to the local server once and never sent back: the dialog shows only the masked form, and leaving the key field blank keeps whatever is stored.

`POST /api/v1/generate/{text,image,speech,music,video,asr}` asks a configured model for one answer. The endpoint names the capability, so a body that disagrees with it is ignored. An answer arrives as one document carrying the text and any media base64-encoded beside its mime type, kind, and dimensions — nothing is written into a project by these endpoints, so a caller decides what to keep. A text request with `params.stream: true` instead answers `text/event-stream`: repeated `delta` frames, then a closing `done` frame with the whole answer. A stream has already sent its status line by the time it can fail, so a failure travels inside that closing frame rather than as a status. Video is the exception — it starts as a handle and is polled at `GET /api/v1/generate/tasks/{id}` until it ends, and a handle the server never issued is missing rather than merely unfinished. Every failure answers the same problem document with the same code in the body and in an `x-error-code` header, and a caller never receives a provider's raw response body — only its message, with any credential that message echoed replaced by the masked form.

A node carrying a generation spec runs on the provider rather than on a local operator, so a run started at `POST /api/v1/projects/current/runs` is what asks a provider on a canvas's behalf. Its answer is filed in the project as an asset bearing the run it came from, the node that asked, the inputs that travelled, and the parameters it was asked with — never the credential those parameters resolved to. An ask answered several times over keeps its first answer on the node that asked and gives the rest a card each. A node that already says or shows something keeps it, and the answer goes on a card beside it joined back to what it came from, so asking again is how a canvas is compared rather than overwritten — and asking once more writes into the card that is there instead of adding a second. An ask that fails leaves the node saying what it said before. A deployment configured without the provider executor refuses such a node before the run starts, and the editor disables the button and says why rather than offering one that cannot work.

Across the top of the editor sit the project's name, a tab for each canvas that is open, where the last save has got to, and what acts on the document as a whole: **Undo** and **Redo**; **Add node**, opening the same quick-add menu a double-click on blank canvas gives and landing the chosen node at the middle of the view; **Group** and **Ungroup** over the selection, offered only when they would do something; **▶ Run** over every selected node a run can carry; **Import…**, filing files from this machine as assets and landing them as nodes where the view is pointing — as do files dragged in from outside the window or pasted in, any number at a time, except that one let go over a card is put into that card in place of whatever it held, and a file that card cannot hold still becomes a node of its own; and the settings and export dialogs, with **Export image** beside **Export** saving the whole canvas as a PNG drawn in the diagram's own coordinates — everything the canvas holds rather than the part on screen, on the workspace colour and without the marks that exist only for the hand, at twice size, giving density back as a diagram outgrows a 4096² picture. The strip under the canvas keeps the tools, the zoom, and the panel toggles: **Fit** frames everything the canvas holds, **Selection** frames what is selected and stays out of reach until something is, **100%** returns to actual size, and the slider reaches any zoom between 5% and 500% with the value read out beside it. A wheel over the canvas zooms toward the pointer, and Ctrl — which is also what a Mac trackpad pinch sends — takes quarter steps of it, for aiming at a detail without overshooting. After the slider come the two buttons that choose what everything is drawn in — **Graphite** or **Paper** — a choice kept on this machine rather than in the document, so a project opens in whichever an eye prefers and a package carries neither. With nothing selected the inspector holds the canvas's own view: which of the three backgrounds sits behind the cards — **Dots**, **Lines**, **Blank** — and whether the minimap stays in the corner; unlike the theme these are written into the document like any other edit, so they are undone, saved, and packed with the work, and the minimap is navigated by clicking or dragging on it, which moves the view to the place the pointer names. `?` opens the list of keys the editor answers to, written down beside the keyboard handler itself and read by the dialog, so the help cannot go stale on its own.

Asking is done in the editor rather than at the API. Selecting a text, image, audio, or video node brings a panel up under it; the same panel is reached through **Generate…** on the node's menu, and through `Enter` on a node a provider can answer, where `Enter` on a text node that already has words edits them instead. The **Prompt** toggle in the editor's footer turns the panel-on-selection off, and `Escape` closes it for as long as that node stays selected. The panel holds the model, the prompt, and the parameters that capability has, each of which says what the global default is on the choice that leaves it out; what is typed is written to the document when focus leaves the field, so a keystroke is neither an undo entry nor a save, while a control that is clicked writes straight through. Choosing a shape gives a node that is still empty that shape. A node that cannot be asked yet says why on the button — nothing typed and nothing connected to, no model of that kind configured, a prompt past its limit, or a deployment with nothing that can reach a provider — and a prompt near its limit is counted out loud beside it. The button becomes **Stop** while a run is going and **Ask again** after one that gave up, which follows that run rather than starting one with nothing to do with it.

What an ask is given is chosen rather than assumed, and nothing is asked of the reader to choose it: the prompt's own words where they name cards, the list kept by hand where there is one, and the wiring otherwise — a prompt that names cards is asking for those and nothing else, so it reads the tokens and the rest of the panel only says so; a list pointed at by hand comes next, in the order it is listed, which is the order it counts for; and a node with neither is given everything the wires bring it, in the order the wires were drawn, a group opened into its members. The field itself folds nothing away and is never anything but the words: empty until something is typed, as tall as the panel gives it, and every reference drawn inside the sentence that names it — what is chosen with `@` is written into the document as `@[node:<id>]` and shown as the card's own name between ticks, the way Markdown writes a code span, so a reference reads where it is written rather than beside it. Typing `@` offers the nodes this one could mean — upstream of it, listed by it, or any other on the canvas holding something — a picture by its thumbnail and a text by its first words; hovering a name summons the whole of what it points at, and backspace takes it out whole rather than a character at a time. Under the field sits what the prompt points at: one entry per card named, in the order the words name them, the picture itself where the card has one and the mark of its kind where it has not — a text and a sound are read and heard rather than seen, so a thumbnail of either would be a lie — and hovering an entry shows the whole of it: the words of a text, the sound playing, the picture large. A name whose card has gone from the canvas is drawn as one that is gone and said below the field, and the button refuses with it rather than sending an ask that quietly means something else. An asset dragged from the assets panel onto the bar — or a file brought from this machine, filed on the way — is wired in beside the node or added to its list, wherever the words leave room for it; a prompt that names its own cards takes nothing from the bar, so nothing dropped there would be read and the bar does not pretend otherwise. A wired-in reference can be moved to the input it belongs on, found on the canvas, or disconnected, a listed one can be dragged into a different place in the list, and each of those is one step of history rather than several.

**Preview** asks `POST /api/v1/projects/current/generate/preview` what the node will send, rather than working it out a second time in the browser: the words exactly as a run sends them, with upstream text folded in under a `[Text 1]` heading of its own, and every reference with its mime type, dimensions, length, size, and the card it came from. One resolver answers both the preview and the run, so the two cannot drift apart — a panel showing three references while a request carries two is the kind of wrong nobody can find from the answer. Anything that will not travel is said outright instead of being left out quietly: a mention naming a node the canvas has never heard of, a file that is not there any more, text cut by so many characters to fit the limit. A node can also be filled without asking for anything at all. **Image from these words** on a text node's menu — with video, audio, and a rewrite beside it — makes a node to the right of the words, wires them into it, and opens its panel with nothing asked for yet, so a choice from a menu cannot spend anything on a provider; and an empty asset node offers what the project already holds, which puts a picture into a node that was waiting without asking for one.

The card carries the state of the run it was asked in: how far that run has got, or a band that says only that it is going where nothing has measured one; a mark with the reason where an ask failed, which leaves what the card held before in place; and how many answers one ask brought back. The inspector lists every ask a node has had rather than only the newest, and every result it holds, with the one the node shows named as such; making another of them the one shown is offered there and on the menu of both the node holding a batch and a card holding one of its answers, and is written into the document like any other edit. Beside the inspector, the **History** tab keeps every ask the project has had, each run read from its own record rather than from whatever the nodes hold now: the cards it was asked of, how it and each of its steps went, and the parameters each step was carried with, narrowable to one card's asks, with one button that asks the same again — retrying a run that failed or was called off in place, and otherwise starting a run of the same cards afresh. At the bottom of the node inspector its JSON is folded away for reading: the node as the document holds it, down to the fields no row mentions, which is what settles a disagreement between what the panel says and what is there, and it can be copied out whole. A card holding a film shows the film's own first frame with a play button over it — a canvas cannot play anything, so that one face is put over the card in the DOM — and the button hands the face to the file itself, controls and all, while the rest of the frame still drags, selects, and wires the node as any other card's does; pausing or ending brings the button back, and a card below the zoom where media stops being drawn leaves the face away with it. Closing a project or switching canvas with a run still going says how many are going and stops none of them: a run belongs to the project, so what it makes is written into it whether or not anybody is still looking at the canvas it was asked from.

Two or more nodes selected brings a bar up over them for what can be done to them together: **Group**; lining them up on the left, the middle, the right, the top, the middle row, or the bottom of the room they take up together; giving them all the widest one's width or the tallest one's height; spreading them out with the same room between neighbours along either axis; and **Delete**. Each is one step of history, an act that would change nothing writes nothing, and what is arranged is the members rather than a group's frame, which stands for them and is left where it is.

Not everything on a canvas is asked of somebody. Selecting one picture brings a row of tools up over its card — **Crop**, **Split**, **Resample**, **Tilt**, **Repaint**, **Describe** — and which of them it offers is the reader's to choose under **Settings** → **Preferences**, kept on this machine rather than in the document, so a bar somebody has tidied stays tidied and travels in no package. The first four are arithmetic on pixels that are already here, so they cost nothing, give the same answer twice, and work in a project with no model configured; `POST /api/v1/projects/current/tools` does them, told the tool, the picture, and the parameters, and nothing else. Each asks its own question first — a proportion, or a region given in the picture's own pixels rather than in the rectangle a card happens to be drawn in; a grid; a size by name or one asked for, and how a picture is to meet a box that is not its shape; an angle to turn and tip by — and refuses what it cannot do before anything is written, whether that is a region outside the picture, a division past its ceiling, or a proportion nobody can read. None of them rewrites the file a card holds. What they make is filed as an asset of its own, named after the picture it came from and carrying the tool, the parameters and the subject as its provenance with no run behind it, because nothing ran; it lands on a card to the right, wired back to what it was made from, so the step reads in the graph as one picture made out of another rather than as a file that changed underneath a node. Every piece of a division arrives in one step of history and all of them are selected, so a sheet cut nine ways can be grouped the moment it lands, and letting go of that step takes the cards and the wires while leaving every file filed. A picture whose file is missing, has changed on disk, or is empty gets the reason on the bar instead of a tool that would fail in a moment reading as the tool breaking, and the inspector says which tool made the picture it is showing and which picture it was made from — offering a run only where one started.

**Repaint** and **Describe** sit in the same row and are hidden by the same setting, but each is an ask rather than arithmetic and costs what an ask costs. Repaint takes a region painted over the picture itself, because a region worth repainting is a shape somebody can see and not one they can give in four integers; what it makes is the two halves of an ask rather than a repainted picture — the marking filed as a mask of its own and wired into the picture's mask port, the words written into that picture's ask — so the repaint is one press from being run and nothing has been spent from the dialog. Describe asks a model that can see to read the picture back as the words that would make it, shows the answer as it arrives so that a model answering about nothing is caught there rather than after a second generation spent on its guess, and files what it said as a text node wired into the picture's prompt, which makes the picture askable again from the words it was read back as.

The column on the other side of the canvas has two faces, chosen at the top of it, and which face is showing is kept on this machine rather than in the document. Each column beside the canvas carries a half triangle flush with the corner it stands in, which folds the whole of that column away and hands its room to the canvas, and the corner of the window it stood in keeps the same triangle turned the other way round, which stands the column back up; which columns are folded is kept on this machine beside the widths they were dragged to, so the editor opens the way it was left. **Project** is the whole of what a project holds, as a tree: folders that hold folders and canvases, and each canvas opening onto the four kinds of thing it uses — **Text**, **Image**, **Audio**, **Video** — with the files themselves under the kind each is filed as, so what a board is made of can be read without opening it. A board is opened by clicking it there, which puts a tab up on the strip across the top, and putting that tab down leaves the board untouched, since a tab is a way of looking at a board rather than the board itself; which boards were open is remembered per project, so a project opens onto the work it was left on. Folders and boards are made, named again, deleted, and dragged somewhere else from the row they are on, each of them one step of history, and what a folder held when it was deleted moves up into the folder that held it rather than going with it — so tidying the tree cannot cost anybody a board. **Assets** is the project's material shelf: the same files read altogether rather than by the board that uses them, cut into the same four kinds. Following a file from the tree turns the column over to the shelf with that one row marked, which is what two faces of one column are for. A click on a file is a question about that file rather than a move on the canvas: the column beside the canvas turns to the inspector and reads it there — the shelf it is filed on, its kind, size, dimensions or length, where it sits in the project, where it came from, what a reader noted about it, and how many cards hold it on this board and in the project — with the picture, the sound, the moving picture, or the words in it shown where they are being read. Going to the cards is asked for separately, as **Focus** on the row and **Focus cards** in the inspector, and is greyed where this board holds none. Every file carries what a reader said about it — the words it is filed under, a note, and a keeper mark that keeps it to hand — and where it came from: brought in, made here by a run, or saved from a node's own work, which the shelf works out from the record a run left rather than from a field free to disagree with it. The shelf narrows by a word matched against the name, the words, the note, and the summary; by shelf, where the kind being read has more than one to tell apart, a sound being filed as either music or a voice; by origin; by keepers; and by every word chosen at once, with the words counted over the whole shelf so that choosing a second one narrows the list instead of emptying it. A node holding a picture, sound, or video is marked as one to hand on the shelf, with the ask it was given as its summary where it had none; a text node's words are written to the shelf as a file of their own, read on the server from the document rather than retyped from the card, and filing the same node again gives back the file that was already made for it rather than a second copy. **From assets…** takes the shelf the other way, from the quick-add menu, from a node's reference bar, and from beside the assistant's about line: one dialog with the same search, shelf, and word controls, in which several files may be chosen at once, saying before anything is taken whether what is chosen will be inserted as so many nodes — one undo, all of them selected — or added to the node that asked, wired in beside it or listed by it according to where that node's own ask takes what it is given from.

Asking can be carried on in words rather than one node at a time, which is what the **Assistant** tab beside the inspector is for. A conversation is about cards: the selection, and whatever feeds those cards, is what a question is asked of, and the head of the panel says so in counts rather than leaving it to be inferred. **Ask** and **Rewrite** send that to a model that writes — Rewrite taking only the text card chosen, so a rewrite cannot wander off into the rest of the canvas — while **Image**, **Video**, and **Audio** go through the same run pipeline a node panel uses, so what comes back is a card on the canvas and an asset in the project rather than something to copy out of a chat window. A card asked about that way feeds the ask over a wire rather than as words quoted into it, which is why the picture that lands is joined to the text it was made from. Nothing is spent until Send is pressed, and a kind with no model configured says which kind is missing and offers the settings rather than answering the ask badly.

What an answer said stays on the canvas. Each kept line can be put on the canvas as a card of its own, written over the text card it was a rewrite of, copied, downloaded, followed back to the card it made or the shelf its file went onto, and a card that came back empty can be asked again from the line that says so without a second card appearing for it. A turn that failed is a line in the conversation rather than a notice that fades: a reader coming back later can see that this was asked and nothing came, and can ask again from that line. A conversation keeps only as much of itself as the window holds, stepping back by increments rather than rendering hundreds of lines at once, and a card a line was about that has since been deleted keeps its snapshot with the line saying plainly that the card is gone. How many conversations a canvas has had, what each is titled, and what each holds is document state, so it is one canvas's record rather than this machine's; for a words ask, the last few lines can travel with the question, and the panel counts out the characters that go so that what is offered is what will be sent.

A project is a plain folder on the machine the server runs on, so saying which one is meant is a question of where to look. On a desktop the operating system's own file dialog answers it. In a browser nothing can be asked, and the alternative was a field waiting for an absolute path — a field only somebody who already knows the path can fill in — so `GET /api/v1/filesystem?path=<dir>&extensions=moka` lists one directory instead and the launcher's **Browse…** draws a dialog out of those listings: the folders to walk through, the files of the kinds asked for beside them, the resolved directory in a bar that can still be typed into and listed, and a way up. What it answers is names and where they lead, never what any of them holds; entries whose name begins with a dot are left out, a listing stops at 1000 entries and says so, and no extension asked for means folders alone. The route is served in the web runtime only — a desktop has a real dialog, and a loopback server answering a question nobody there needs to ask is a wider surface for the same price — and it carries the standing caveat of an API with no authentication: whoever can reach the port can ask it, which is why [docs/deployment.md](docs/deployment.md) says what binding it off loopback means.

A project travels as one `.mokapkg.zip`, written by `POST /api/v1/projects/current/export` and read back by the launcher's **Import project**. **Export** asks two questions first and both start off: whether the record of the runs this machine made goes along, and whether assets no node points at are left out. Answering neither gives the package of the work — the document, its assets, and a manifest naming every rule that skipped a file with the count and the room it freed — with the run that made each generated asset, and the conversations had over each canvas, taken off it, so what arrives somewhere else says how a thing was asked for without saying which machine answered or what was said to it there. Ticking the first gives a backup for moving one's own work to another computer, which keeps those records and those conversations and says in its manifest that it did; ticking the second trades the material shelf for size, and the question counts what would be left behind before the choice is made rather than after. Model configurations, API keys, the prompt library, the recent-project list, and the logs are application state rather than project state, so neither kind can carry them — the dialog says so instead of leaving it to be discovered. An export stops and names the assets it cannot find rather than writing a package that opens broken, and offers to go ahead with the gap flagged in the manifest and in the toast that reports it. `includePersonalHistory` and `onlyReferencedAssets` are the two request fields, and a body carrying neither asks for the package of the work. Importing takes a package made by this build or the one before it and refuses a later one with the range it does read; a package that does not say it carried the run records is cleaned to what this build keeps on the way in, so a file that has been round an older build does not bring that build's history with it.

Beside the boards a project keeps a cutting room: a timeline of the video, audio, and text a project's files are cut into. A picture, a film, or a sound is dragged from the shelf onto a row and then moved, trimmed, split, duplicated, or detached from its audio, with a magnet snapping edges onto the playhead and each other and one step of history behind every gesture; two butted blocks meet through a transition — seven kinds, a window shaped by dragging the seam or a slider, the whole chain re-laid in one undo — and words are written on the Text page or brought in as a whole `.srt` and written back out as one, with an inspector that edits whatever is chosen from a clip's pace and grade to the timeline's frame rate and background. The picture is composed live under the playhead and the transport plays the cut with sound, exactly or approximately as the machine's own decoders allow, and `Export video…` renders the timeline to an MP4 through the machine's own ffmpeg, filing the file into the project as an asset. The preview and the export are two engines — a browser canvas that approximates and an ffmpeg render that is exact — and the room says which one it is showing rather than letting the difference be discovered; a machine with no ffmpeg is told so in the export dialog, and nothing else in the room changes.

A project also keeps a story room, reached from the same menu the other rooms are. A telling is written there rather than drawn: a premise and how long it should run, the episodes it is told in, the characters, places and things it is made of, and then the acts, shots and lines of each episode, one board per episode. Every one of those steps is a batch of asks sent to the configured models and filed back into the project as a card, a picture, or a shot of an episode, which means a reader can stop between any two of them, change what came back, and go on. The last step lays the shots that have been filmed end to end on a timeline of the telling's own — with the lines said in them as a caption track — and hands that timeline to the cutting room, or renders it to one file through the same ffmpeg the cutting room uses. Nothing about the room is a second way to make a project: a story is part of the document, its pictures and films are ordinary assets on the shelf, and its timeline is an ordinary timeline that can be cut by hand afterwards.

See below for what each of the five steps makes and what it needs, and [docs/deployment.md](docs/deployment.md) for the batch limits a server sets.

See [docs/security.md](docs/security.md) for how credentials are protected and what that protection does not cover, and [docs/deployment.md](docs/deployment.md) for running the standalone server.

## Story

Five steps turn a premise into a film, and each of them is a batch of asks a reader can look over before going on:

```text
  1 Idea                 2 Outline              3 Elements           4 Storyboard          5 Edit
  premise, running       the episodes it        characters,          acts, shots and       the shots laid
  time, frame,           is told in, each       places, things,      lines per episode,    end to end on a
  style, source text     with a synopsis        each described,      drawn and filmed      timeline, captions,
  ──────────────         ──────────────         drawn and agreed     shot by shot          rendered to one file
  text                   text                   text + image         text + image + video  ──▶ cutting room
```

| Step         | What it asks for                                                                                                                                                                            | Filed as                                                                                                                                       | Capability                                           |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------- |
| 1 Idea       | outlines the premise into chapters (or splits an uploaded manuscript as it stands)                                                                                                          | the story's brief and chapters                                                                                                                 | text                                                 |
| 2 Outline    | expands, condenses, or resends the chapters, saying what it costs first                                                                                                                     | chapter titles and synopses                                                                                                                    | text                                                 |
| 3 Elements   | the cast of the chapters; a main picture per element, and four views per character                                                                                                          | `StoryElement` cards on the document; pictures as assets                                                                                       | text, image                                          |
| 4 Storyboard | acts, shots, lines, and shot sizes per episode; a picture per shot; a film per act or per shot; every line read in the voice of whoever says it, and the music under the act, both optional | `StoryAct` / `StoryKeyframe` on the document; pictures, films, and sound as assets                                                             | text, image, video, speech and music (for the sound) |
| 5 Edit       | nothing — it assembles what the fourth step filmed, voiced, and scored                                                                                                                      | one timeline, captions on a text track, each reading on a voice row inside the shot it is said in and the score on a music row, a rendered MP4 | video (for the shots), ffmpeg (for the render)       |

Two things about the room are worth saying out loud. A step is only as ready as the one before it: the elements step waits until the chapters are confirmed, the board waits until every element is settled, and the edit waits for one filmed act — the room greys out what cannot be asked yet and says what is missing. And a generated element's file is named neutrally on the shelf (`element art-3f9a1c02`, not "阿澈 main picture"), since the server files a batch's drawings without reading the document — the room shows the real name on the card, and the shelf shows the file.

What the room does not do is as much a part of it. A batch is watched by its record rather than by its words, so a long reading shows how far along it is and not the text arriving — a batch record has to be there for the next boot to pick up, and a stream and a record are two state machines. A telling longer than a model can be handed at once is cut and read in parts: the manuscript into the pieces a chapter is written from, and the chapters into the batches their cast is read from, one ask after another and never two at a time, with both boundaries the reader's to set under **Settings** → **Preferences** → **Story room**, since how much a model holds is a property of the deployment rather than of the telling. What a part names is added to the cast beside what the parts before it found, and a name two parts both found is one element carrying the chapters both of them read it in — the chapters are listed under the telling's own numbers, so that is what they are filed against even where a part holds only a few of them. Films are made per act or per shot, and the lines are carried as captions: the lines may also be read aloud, one ask a line and each in the voice of whoever says it, and the music and sound under an act asked for as well, both optional pieces a reader asks for one act at a time — a telling with no sound at all is still a telling, and the sound lands on rows of its own under the film rather than being mixed into it. A speaking part's voice is kept on the story itself: the model that reads it, the tone it reads in, and the manner of the character saying it, each falling back in turn to the narrator's voice, the machine's own pick for speech, and the deployment's default, so one character may be read by one model and the rest by another. A batch carries one model, so a press that reads a whole act is grouped by whoever speaks and sent one wave per model, one after another; each line is asked in the words of that line alone, and a line already read is not paid for twice. What comes back is laid inside the shot the line is said in, and a reading too long for its shot is read faster instead of being cut — no further than 1.35×, past which it would stop sounding like a voice, and said to run over the shot rather than passed off as fitting, which the board tells the reader before anything is rendered. Assembling is the room's own press, and exporting assembles first whenever the telling has moved since the film was laid down, so what is rendered is never a film of a telling that is no longer there. A score is asked of the music default: speech and music are capabilities of their own, so a score is never answered by whatever reads the lines, and a deployment that keeps one of the two configures the other. Reading the chapters again, or a board again, throws away what no longer matches what came back — the dialog says how much that is before it happens, and a part's reading only adds, since a part never saw the chapters it was not asked about. And the fifth step owns only the clips it laid down: anything added to that timeline by hand afterwards is left where it is, even where the story's own clips are re-laid around it. Subtitles live on the timeline's text track and are burned in by the export path; the room writes no `.srt` of its own.

## Quality and packaging

```sh
make check
make test
make package-web
make package-macos
make package-windows
make cross-package-windows
make clean
```

`make check` is the full baseline gate: formatting, lint, typecheck, the production web build, the frontend Vitest suite, Rustfmt, Clippy with warnings denied, and the backend `cargo test` suite. `make test` runs just the two test suites (Vitest and `cargo test`) without the lint/format/build gates. `npm run test:e2e` drives the built application in a real browser through Playwright: the launcher-to-editor critical path, missing-asset recovery, a model-settings round trip, a generation driven end to end against a stand-in provider the suite brings up itself, a conversation asked for a picture that lands on the canvas and is filed as an asset, a picture cropped from the row of tools over its card, and a telling taken from a premise through chapters, cast, board, one filmed act, an act's voice and score to a timeline the cutting room opens on, and a telling whose every line is read in the voice of whoever says it and laid down where that line is said — each against a server started with a temporary metadata directory and a master key generated for that boot, since server mode will not invent one and a model can hold no credential without it.

`package-web` stages the built site and a native `moka-server` binary under `release/`. Native app packaging is intentionally host-native: build macOS artifacts on macOS and Windows installers on Windows. Release signing and macOS notarization require organization-specific credentials and are not part of this baseline.

`cross-package-windows` cross-compiles the Windows NSIS installer (`-setup.exe`) on macOS using the `x86_64-pc-windows-gnu` Rust target. It requires the mingw-w64 toolchain and NSIS (`brew install mingw-w64 makensis`); the Rust target itself is installed automatically if missing. The build sets `LC_ALL=en_US.UTF-8` because makensis crashes with `std::bad_alloc` when a non-UTF-8 locale is active (see NSIS bug 1165). `make clean` removes `dist/`, `release/`, `src-tauri/target/`, and TypeScript build caches.

## Comparison workflow

1. Compare **Component lab** and **Token parity** in a browser and Tauri at the same window size.
2. Resize each runtime and use **Interaction lab** controls to ensure stage destruction/recreation is clean.
3. Test high-DPI scaling and direct navigation to `/showcase`, `/playground`, and `/tokens`.
4. Verify no remote fonts, images, CDN scripts, or Tauri JavaScript APIs are required by the frontend.
